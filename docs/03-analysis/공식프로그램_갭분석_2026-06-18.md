## 1. 핵심 요약

- 본 검증은 **확정(confirmed=true) 갭 49건**을 대상으로 하며, **호환성 파괴/데이터 손실 위험(P0~P1)이 13건, 신규 기능(주로 정당·후원회 계열 출력물)이 14건**으로, 후보자/후원회 단건 흐름은 견고하나 **일괄등록·정당계열·국세청·결산 SSOT 일원화**에서 격차가 집중된다.
- **즉시 조치 P0 1건**: 복구(import-sqlite) overwrite가 `customer`·`customer_addr`·`acc_rel`·`accbooksend`를 **org 필터 없이 전역 삭제**(코드 확인 완료, L278~284) — 단일 Supabase prod 환경에서 한 기관 복구가 타 기관 거래처·코드매핑을 영구 파괴.
- **반복되는 SSOT 괴리 2종이 다수 갭의 근본 원인**: ① 마이너스 수입 보정(`computeBalances`)을 결산화면·제출 .txt가 우회 → OPINION/export와 수치 이원화, ② 차입금 부호 규칙(가액 합계 차감)이 estate 전 경로에서 미강제 → 재산 가액 과대계상.
- **일괄등록(batch-import) 파서가 지출 양식의 'B열 경비' 시프트·지출방법·지출유형·후원금센터 9컬럼·custType 10종을 미처리**해 후원회·정당 지출 import 시 전 행 오매핑.
- 이미 공식보다 앞선 영역(HWPX 서식 자동채움, 자금원 잔액가드, 영수증 채번 SSOT, SQLite FK-orphan 방지)은 4번에 명시.

## 4. 이미 충분히 커버됨 (안심용)

- **HWPX 서식 자동채움(공식보다 앞섬)**: 서식 7/22-1/22-2/22-3/22-4 토큰치환·동적 행 복제 빌더가 (예비)후보자 경로에서 완비. 정당/후원회로의 확장만 남음(2번 참조).
- **자금원 잔액가드**: 지출 입력 시 자금원별 시간순 잔액·경고 — 공식에 없는 부가 안전장치.
- **영수증 채번 SSOT(`receipt-no.ts`)**: batch_receipt와 export-sqlite가 동일 채널 공유, 형식이 acc_sec_cd 기반으로 정합.
- **SQLite 라운드트립 호환 핵심**: ACC_INS_TYPE→EXP_TYPE_CD 정규화, `stripAppOnlyAccBookColumns`(acc_time), `selectReferencedCustomers`(FK-orphan 방지)로 후보자/후원회 .db 호환이 정밀.
- **acc_book 정렬 SSOT(`compareAccDateTime`)**: 제출용 누계 장부(reports·HWPX·income-expense-book·fund-realloc)에는 incm_sec_cd 수입우선 tie-break가 이미 적용 — 음수잔액 핵심 리스크는 완화됨(주 조회 API 일관성만 보강 대상).
- **지출결의서 양식 정합**: 코드 생성물이 공식 지출결의서.xls와 셀·문구·병합까지 바이트 단위 일치(스냅샷 테스트만 권고 — 갭은 P3).
- **delete_org_data RPC**: 역-FK 순 원자적 org 삭제 — batch_delete RPC의 선례로 재사용 가능.
- **지원금내역 exp_sec_cd=42**: 자체 시드(codevalue.json cv_id=42='지원금', cs_id=4)로 검증된 상수 — phantom 코드 아님(하드코딩 제거는 P3 nice-to-have).
