# 정치자금 수입·지출부 생성 주의사항 (개발/운영 참고)

> **대상**: 정치자금 수입·지출부(서식 7/22-4)·회계보고서(22-1/22-2)·자료백업(SQLite)을 **생성하거나 그 코드를 수정**하는 사람.
> **목적**: 2026-06 (v0.16.0.0, PR #86)에서 해결한 "수입·지출부 (계정×과목) 잔액 깨짐" 문제가 **다시 들어오지 않도록** 하는 제도적 지식.
> **한 줄 요약**: `acc_book`은 **실거래 원본**. 선거비용/외 분할은 **보고 생성 시점에만** 메모리에서 계산한다. 선거비용 판정은 **과목(`item_sec_cd` 86/87)** 으로만 한다.

관련: [income-expense-item-allocation.design.md](../02-design/features/income-expense-item-allocation.design.md) · [공식프로그램_갭분석_2026-06-18.md](../03-analysis/공식프로그램_갭분석_2026-06-18.md)

## 0. 이 문서를 펼쳐야 하는 순간

- 수입·지출부 / 회계보고서 / 자료백업(.db) **출력에 숫자가 안 맞을 때**.
- 새 보고서·HWPX 서식·export 경로를 **추가할 때** (분할·분류·정렬을 직접 다루게 됨).
- `acc_book`에 컬럼을 **추가**하거나, 선거비용·자금원 **집계 로직을 새로 짤 때**.
- 윈도우 공식 프로그램(PFund2)으로 **라운드트립**할 때 계정별로 행이 사라지거나 잔액이 음수로 찍힐 때.

## 1. 왜 잔액이 깨지는가 (근본 원리)

돈은 **fungible**(섞이면 출처 구분 불가)이다. 그래서:

- **선거비용/선거비용외는 "지출"의 성격**이다. 어떤 돈을 어디에 썼느냐가 정한다.
- **수입의 과목**은 그 수입으로 *실제 충당한 지출의 과목*에 맞춰 태깅돼야 한다. 공식 `Fund_Data_1.db`가 바로 이 구조다.
- 우리 입력 데이터는 수입을 대부분 과목 `86`(선거비용)으로 몰아 기록했다. → 통장 **총잔액은 항상 정확**하지만, **(계정 × 과목)으로 슬라이스하면** 한 과목은 수입>지출(잉여), 다른 과목은 수입<지출(음수)로 갈라진다.

**핵심**: 총현금은 안 깨진다. 깨지는 건 *(계정×과목) 칸별 잔액*뿐. 그래서 해법은 "수입을 충당 과목으로 재태깅(분할)"이다 — 데이터를 바꾸는 게 아니라 **보고서를 만들 때만** 재배치한다.

## 2. 절대 규칙 — 불변식 I1~I4

전 경로(`buildLedgerRows`)가 공유하는 4가지. **어기면 법정장부가 틀어진다.**

| # | 불변식 | 의미 |
|---|---|---|
| **I1** | 합 보존 | 배분 후 자금원별 **수입합·지출합 불변**. 분할만 일어나고 증발·증식 0. |
| **I2** | 무음수 | 모든 (계정×과목) 시간순 **최저잔액 ≥ 0** (통장 ≥ 0 가정). |
| **I3** | 멱등 | 같은 raw 입력 → 같은 배분 결과. `buildLedgerRows∘buildLedgerRows = buildLedgerRows`. |
| **I4** | **지출 과목 불변** | 사용자가 지정한 **지출의 과목(선거비용 86 / 선거비용외 87)은 절대 변경 금지**. 계정(자금원)은 바뀌어도 과목은 안 바뀐다. |

> **I4가 가장 중요하고 가장 깨지기 쉽다.** "선거비용으로 설정한 지출은 무조건 *다른 계정의* 선거비용으로 잡힌다." Pass1이 지출을 다른 자금원으로 옮겨도 `...r` 스프레드로 `item_sec_cd`를 보존하고, Pass2는 **수입만** 재태깅한다 — 지출은 항상 `effectiveItemSecCd = item_sec_cd`. (회귀가드: `item-allocation.test.ts`, `ledger-allocation.test.ts`)

## 3. 분할은 "보고 생성 시점"에만 — acc_book은 건드리지 않는다

**2026-06-20 사용자 결정 (영구화 롤백)**:

> "지출내역의 데이터까지 금액을 나누면 안 됩니다. 보고자료를 만들 때만 금액을 나눠야 합니다."

따라서:

- ✅ `acc_book` = **실거래 원본**. 분할 행을 **저장하지 않는다**.
- ✅ 분할은 보고/출력 생성 시 **in-memory로 `buildLedgerRows` 호출** → 그 결과로만 표·시트·.db를 만든다.
- ❌ `acc_book`에 slice0 UPDATE / 이동분 INSERT 하는 **영구화 경로는 폐기**됨 (`apply-item-allocation` 라우트·`scripts/016`·`017` RPC → `scripts/018`로 drop 완료).
- 폐기된 설계 흔적: design.md의 **§3·§4.3~4.6은 무효** (문서 상단 배너 참고). 유효한 건 §1·§2·§4.1·§4.2·§5·§6·§7.

> 새 출력 경로를 추가할 때 "DB에 분할을 미리 저장해두면 편하지 않을까?" 하는 유혹 → **금지**. 실거래가 왜곡되고 영수증·증빙 FK가 꼬인다.

## 4. 분류 SSOT — 선거비용/외는 오직 과목(`item_sec_cd`)

선거비용 판정에 쓸 수 있는 후보가 셋 있고, **둘은 함정**이다:

| 소스 | 쓰면? | 이유 |
|---|---|---|
| `item_sec_cd` (과목, 86/87) | ✅ **이것만** | 과목명을 `getName`으로 풀어 분류. 사용자가 직접 지정한 값. |
| `exp_sec_cd` (지출유형) | ❌ 금지 | **미입력(0)이 많다.** `>0`으로 판정하면 멀쩡한 선거비용이 전부 선거비용외로 오분류 (실제 총괄표 버그였음). |
| `acc_sec_cd` (계정/자금원) | ❌ 금지 | 자금원(82~85)일 뿐 선거비용 여부와 무관. |

**SSOT 함수**: `report-summary-builder.ts`의 `classifyExpenseCategory(itemName)`
- `"선거비용외"` 포함 → 선거비용외 (먼저 검사)
- `"선거비용"` 포함 → 선거비용
- 불명 → **선거비용외** (보수적 기본값, 선거비용 과대계상 방지)

**이 기준을 쓰는 모든 곳이 일치해야 한다**:
- `report-summary-builder.ts` — 22-1 총괄표(`buildReportSummaryModel`), reports Excel 총괄표(`aggregateSummaryByAccount`)
- `org-metrics.ts` — 대시보드 선거비용 카드 (`electionExpenseItemCds.has(item_sec_cd)`, **`exp_sec_cd>0` 아님**)
- `settlement-calc.ts` — `electionExpenseItemCds = Set([86])`
- `reimbursement-aggregator.ts` — 보전청구서 (claim-form과 동일 기준)

> ⚠️ 과목 cv_id를 **하드코딩하지 말 것**. `94=기명/95=익명`인데 `95=기명`으로 반전 입력된 실제 버그가 있었다. 항상 **과목명(`getName`)으로 분류**한다. (cv_id 상수는 86/87처럼 의미가 고정된 것만.)

## 5. 자금원 분류 SSOT — `acc_sec_cd` 82~85

`funding-source.ts`의 `FUNDING_SOURCE_BY_ACC_SEC_CD` (후보자 계정 `cs_id=10`):

| `acc_sec_cd` | 자금원 |
|---|---|
| `82` | 보조금 |
| `83` | 보조금외 |
| `84` | 후보자자산 |
| `85` | 후원회기부금 |

과목(`cs_id=11`): `86`=선거비용, `87`=선거비용외정치자금.

- 분류는 `classifyFundingSource(acc_sec_cd, accSecName?)` 하나로. 코드 우선, 폴백은 이름 매칭.
- **후보자**는 수입/지출을 `incm_sec_cd`(1/2)로 구분하고 계정은 82~85 공용. **후원회**는 정반대 — `acc_sec_cd`가 곧 수입(1)/지출(2) 플래그다. 둘을 헷갈리면 집계가 붕괴한다.

## 6. 배분 파이프라인 — `buildLedgerRows` = Pass0 → Pass1 → Pass2

**SSOT**: `app/src/lib/accounting/ledger-allocation.ts`. 순수 함수. 표시·reports·HWPX·export 전부 이걸 호출한다 (이원화 금지).

```
raw acc_book → Pass0 adjustNegativeIncome → Pass1 reallocateFundSources → Pass2 allocateIncomeToItems → LedgerRow[]
```

| Pass | 파일 | 책임 |
|---|---|---|
| **Pass0** | `adjust-negative-income.ts` `adjustNegativeIncome` | 음수 수입("계좌입금오류반환" 등)을 양수 지출로 정규화. |
| **Pass1** | `fund-realloc.ts` `reallocateFundSources` | 자금원 음수잔액 해소 — 지출을 **계정 간** 이동. **과목은 불변(I4)**. |
| **Pass2** | `item-allocation.ts` `allocateIncomeToItems` | 자금원 확정 후, 수입을 **충당 과목으로 재태깅**(필요 시 분할). 지출은 원과목 유지. |

**Pass2 알고리즘** (자금원별 독립, `compareAccDateTime || incm_sec_cd(수입 먼저) || acc_book_id` 정렬):
1. 수입 → 원과목 풀(FIFO 슬라이스 큐)에 적립.
2. 양수 지출(과목 M) → M 풀에서 시간순 차감. 부족하면 다른 과목 풀(코드 오름차순)에서 끌어와 **M으로 재태깅**(수입 슬라이스 분할 → `item-moved`).
3. 환급/0 지출(`effectiveAmt ≤ 0`) → 원과목 유지, 수입 소비 안 함.
4. 잉여 수입(미충당) → 원과목 유지(`item-keep`).
5. 수입이 과목 경계를 넘을 때만 분할(`splitGroupId` = 원 `acc_book_id`).

**워크드 예시 — org11 자금원 85(후원회기부금)**:
- raw 수입 전부 과목86 = 9,430,000. 지출: 86=4,290,015, 87=5,007,485(87 수입 0).
- Pass2: 87 지출 5,007,485 발생 시 87 풀이 비어 86 풀에서 5,007,485를 끌어와 87로 재태깅.
- 결과: **85×87 잔액 0**, **85×86 잔액 +132,500**(잉여, 원과목). 합 보존 = 9,430,000. cash 132,500 = 실통장. ✔

**적용 대상**: **후보자 계열 org만** (자금원 계정 82~85 사용). 비후보자(후원회·정당)는 `buildLedgerRows` 미적용 — 종전 동작 그대로. (가드 상수는 코드의 `CANDIDATE_SEC_CDS` / `acc_sec_cd ∈ 82~85` 참조.)

## 7. 정렬·라운드트립 주의 (음수 누계의 진짜 원인)

수입·지출부는 **누계 잔액**을 찍는다. 같은 날 지출이 수입보다 위에 오면 **그 줄에서 일시적으로 음수**가 보인다. 막는 장치:

1. **정렬 SSOT**: `acc-book-sort.ts` `compareAccDateTime` = `acc_date → acc_time`. 동시각·미입력은 호출부가 `|| incm_sec_cd`로 **수입(1) 먼저** tie-break (잔액 음수 방지).
2. **`acc_time` 은퇴 중**: 거래 시각 입력 UI 제거됨(전부 NULL). `scripts/019_drop_acc_time.sql`로 컬럼 제거 예정 — **prod 배포 후 적용**(코드는 drop-safe). 정렬은 사실상 `acc_date` → `수입 먼저` → `acc_book_id`로 결정된다.
3. **export 라운드트립**: 공식 PFund2는 `acc_time`이 없어 `acc_date → acc_sort_num`으로 정렬한다. 우리 데이터는 `acc_sort_num`이 비어(NULL) 같은 날 수입이 지출 뒤로 밀린다 → 윈도우 프로그램에서 누계 일시 음수.
   - **해법**: `fillExportSortNumbers(rows)` 가 정규순서(`compareAccDateTime → 수입 먼저 → id`)로 `acc_sort_num`을 1..N 재부여.
   - ⚠️ **반드시 `stripAppOnlyAccBookColumns`(acc_time 제거) *이전에* 호출.** strip 후엔 정렬키가 없어 무력화된다.
   - `fillExportSortNumbers`는 **행 객체 참조** 기준으로 rank를 매긴다. `acc_book_id` 기준 Map은 `acc_book_bak`처럼 같은 id가 여러 백업 행으로 중복될 때 충돌하므로 금지.

## 8. 생성 경로별 체크포인트

수입·지출부/보고서를 만드는 5개 소비처. 전부 **보고 시점에 `buildLedgerRows`를 호출**한다.

| 경로 | 파일 | 주의 |
|---|---|---|
| 수입·지출부 화면 | `app/dashboard/income-expense-book/page.tsx` | 후보자 org면 in-memory 분할 표시. |
| 배치 리포트(Excel) | `app/dashboard/reports/page.tsx` (`allocateReportRecords`) | 13컬럼 수입·지출부, 계정+과목 조합별 시트. |
| HWPX 서식 7 / 22-4 | `app/api/hwpx/income-ledger/route.ts`, `app/api/hwpx/accounting-report/route.ts` | 22-4는 비고 1열 추가(form-7=13 / 22-4=14컬럼). |
| 회계보고서 22-1/22-2 | `report-summary-builder.ts`, `election-expense-summary-builder.ts` | 22-1 선거비용 합 == 22-2 합 (교차검증 테스트). §4 분류 SSOT 공유. |
| 자료백업(.db) | `app/api/system/export-sqlite/route.ts` (`allocateCandidateAccBookForExport`) | §7 정렬 + 아래 SQLite 함정 3종. |

**export-sqlite 함정 3종** (각각 실제 버그였음):
- **app-only 컬럼 leak** → `stripAppOnlyAccBookColumns`로 `acc_time`·`claim_amt` 등 제거. 안 하면 `table ACC_BOOK has no column named X`로 export **전체 abort**.
- **지출방법 코드 → ACC_INS_TYPE** → 3자리 PAY_METHODS("118","585")가 공식 `CHAR(2)`에 안 들어가 **지출부 통째 드롭**. `normalizeOfficialExpenseRow`가 `EXP_TYPE_CD`로 옮기고 `ACC_INS_TYPE` 비움.
- **CUSTOMER org 필터 → FK orphan** → `acc_book.cust_id`는 org 경계(공유 익명·타org)를 넘나든다. org_id로 필터하면 참조 거래처가 빠져 윈도우 프로그램이 조인 시 **계정별로 행을 드롭**. `selectReferencedCustomers`로 실제 참조된 cust_id만 선택.

## 9. 제출 전 검증 체크리스트 (운영자용)

수입·지출부를 선관위에 내기 전, 또는 코드 변경 후:

- [ ] **총현금 일치**: (수입 총합 − 지출 총합) == 통장/현금및예금 잔액.
- [ ] **칸별 무음수**: 각 (계정×과목) 수입·지출부 누계가 **음수로 안 찍히는지** (특히 같은 날 수입/지출 섞인 줄).
- [ ] **선거비용 교차일치**: 보고서 22-1 선거비용 합 == 22-2 합 == 대시보드 선거비용 카드 == 보전청구서 선거비용 합.
- [ ] **지출부 존재**: export .db를 윈도우 프로그램에 로드 → **지출부가 통째로 비지 않는지** (ACC_INS_TYPE 이슈).
- [ ] **계정별 누락 없음**: 윈도우 수입·지출부에서 특정 계정만 행이 사라지지 않는지 (FK orphan).
- [ ] **환급 반영**: 환급(음수 지출) 행이 집계에서 빠지지 않았는지 (§10 acc_amt 필터 함정).
- [ ] **공식 대조**: 가능하면 `data/송파` 등 공식 프로그램 출력 PDF와 자금원별 수치 직접 대조.

## 10. 흔한 실수 (anti-patterns)

| 하지 말 것 | 결과 | 대신 |
|---|---|---|
| `exp_sec_cd > 0`로 선거비용 판정 | 미입력(0)이라 전부 선거비용외 오분류 (총괄표 버그) | `classifyExpenseCategory(getName(item_sec_cd))` |
| 과목 cv_id 하드코딩 (`95=기명`) | 반전 입력 시 집계 붕괴 | 과목명으로 분류 (`getName`) |
| `acc_book`에 분할 영구화 | 실거래 왜곡, 증빙 FK 꼬임, 사용자 원칙 위반 | 보고 생성 시 `buildLedgerRows` in-memory |
| 집계에서 `acc_amt > 0` 필터 | 환급(음수 지출) 누락 → 과대계상 | `acc_amt !== 0` |
| `fillExportSortNumbers`를 strip *후* 호출 | acc_time 없어 정렬 무력화 → 음수 누계 | strip **이전** 호출 |
| export 시 app-only 컬럼 strip 누락 | `no column named X` → export 전체 abort | `stripAppOnlyAccBookColumns` 확장 |
| CUSTOMER를 org_id로 필터(data1/data2) | FK orphan → 계정별 수입지출부 누락 | `selectReferencedCustomers` |
| 분할을 표시/영구화로 이원 구현 | 두 경로 결과 불일치 | `buildLedgerRows` 단일 SSOT |
| Pass2에서 지출 과목도 재태깅 | I4 위반 — 선거비용↔외 뒤바뀜 | 지출은 `effectiveItemSecCd = item_sec_cd` 고정 |
