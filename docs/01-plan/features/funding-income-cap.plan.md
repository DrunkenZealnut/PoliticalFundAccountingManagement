- 기능: `funding-income-cap`

## Executive Summary

| 관점 | 내용 |
|------|------|
| **Problem** | 재배분 후 제출보고서에서 후원금(85) 등 자금원의 수입/지출이 실제보다 부풀려져(오준석 2026: 후원금 수입 9,430,000 → **9,647,166**) 실수입 초과로 표시. **진단 결과 근본원인은 재배분 알고리즘이 아니라 데이터**: 내부 계정이체를 수입 +/−로 기재한 4건(순합 0)을 `adjustNegativeIncome`(Pass0)이 지출로 전환하며 자금원 gross 수입을 **gross-up**. 통장 총잔액 0(균형)·Pass1 정상이라 **초안의 가설 A(진짜 부족)·B(Pass1 엣지) 모두 기각** |

| **Function/UX** | 4건 없이도 제출보고서 각 (계정×과목) 잔액 0(83×86·84×86·84×87·85×86·85×87 전부 검증). 향후 음수수입 유입 시 스캔이 경고 |
| **Core Value** | "받은 수입 이상을 그 자금원에서 지출"이라는 성립 불가 표시 제거 + 원인이 **데이터(내부이체 오기재)**임을 확정하고 재배분 로직은 정상임을 입증(불필요한 코어 개조 회피) |

## 0. 진단 결과 (2026-07-01) — 근본원인 확정·해결

**실데이터(Supabase org11, 2026 오준석후보) 진단으로 근본원인이 이 문서 초안의 가설 A/B 어느 것도 아님이 밝혀졌다. 아래 §1~§10은 진단 전 초안이며, 본 §0가 최종 결론이다.**

### 0.1 진짜 근본원인 — 음수수입 gross-up (가설 A·B 모두 기각)
- **가설 A(통장 부족) 기각**: org11 통장 총잔액 = **0**(완벽 균형, 수입 34,932,579 = 지출 34,932,579).
- **가설 B(Pass1 엣지) 기각**: Pass1 자금원 재배분 정상, 순액 잔액 0 유지(84 부족 −413,483 → 85 잉여로 정상 흡수).
- **진짜 원인**: 후원금(85) 계정에 **내부 계정이체를 수입 +/−로 기재한 4건**(#370 +108,583, #371 −108,583, #455 −108,583, #456 +108,583; 순합 0)이 존재. `adjustNegativeIncome`(Pass0)이 음수수입 2건(−217,166)을 양수 지출로 전환 → 후원금 gross 수입이 9,430,000 → **9,647,166(+217,166)**으로 부풀려짐. 초과액 217,166 = 108,583×2.
- 단계별 추적: raw→Pass0에서 정확히 +217,166 발생, Pass1~4는 순액 불변.

### 0.2 왜 그 4건을 넣었나 — 이미 해결된 문제였음
- 사용자 증언: "계정-과목별 지출보고서 마지막 잔액이 0이 안 돼서(환급 #367 −108,583이 한 과목에 −, 다른 과목에 +로 갈림) 없애려고 4건을 넣었다."
- 그러나 **현행 재배분 SSOT(Pass0→L→1→2→3→4, v0.31.0.0)의 Pass3(`zeroItemBalances`, 과목잔액0)가 그 ±108,583 갈림을 이미 자동 해소**한다(수입 재태깅). 즉 4건은 **불필요한 수동 plug**였고 gross-up 부작용만 유발.
- 검증: `buildLedgerRows` == `buildAdjustedAccBook`(persist-allocation이 내부적으로 buildLedgerRows 호출), **4건 삭제 후 모든 (계정×과목) 잔액 0** 확인. 후원금 수입 = 9,430,000 정상 복귀.

### 0.3 해결 및 방침 (사용자 승인)
- **해결(완료)**: 4건 삭제 → 현행 SSOT가 모든 잔액 0. **재배분 코어 코드 수정 불필요.**
- **환급 처리**: 현행 Pass3 방식(수입 재태깅으로 과목잔액0) **유지**.
- **재발방지(구현 완료)**: `app/scripts/scan-income-gross-up.mjs` — 음수수입(gross-up 위험) 조기 감지. org11(2026) clean, org9(2022)에 유사 1건(#97 계좌입금오류반환 −500,000) 감지.

### 0.4 plan 재정의
아래 §3의 "자금원 수입 한도 검증 게이트"(초안)는 **이 케이스엔 부적합**하다(gross-up 후에도 잔액 0이라 게이트를 통과). 본 기능의 실질은 **음수수입 gross-up 감지·경고**로 좁혀진다(스캔 구현 완료). 후속 옵션: (a) 스캔을 CI/배포 전 점검 편입, (b) 수입 입력 UI에서 음수수입 경고·계정이체 기능으로 유도, (c) org9(2022) 옛 주기 유사건 정리(우선순위 낮음).

## 1. 배경 / 문제 (진단 전 초안 — §0가 정정)

### 1.1 현상 (사용자 보고)
후보자 재배분 **후** 최종 지출보고서/산출물에서 후원금(자금원 85)에 배정된 지출 총합이 실제 후원금 수입(9,430,000원)을 **초과**한다. 회계상 한 자금원(수입계정)에서 그 자금원이 받은 수입보다 더 많이 지출할 수 없으므로, 이는 성립 불가 상태다. 사용자 지시: **"지출 재분배 시 하나의 기준이 더 들어간다 — 수입계정의 총합(각 자금원 수입 한도)은 지켜져야 한다."**

### 1.2 현행 재배분이 한도를 다루는 방식 (조사 결과)
재배분 SSOT는 `lib/accounting/ledger-allocation.ts` `buildLedgerRows` = **Pass0→L→1→2→3→4**:

| Pass | 파일:함수 | 역할 |
|------|-----------|------|
| Pass0 | `adjust-negative-income.ts adjustNegativeIncome` | 음수 수입 → 양수 지출 정규화 |
| PassL | `loudspeaker.ts applyLoudspeakerAnchor` | 확성기(540,000) 지출을 계정 84·과목 86 강제 + Pass1 이동 제외(protectIds) |
| **Pass1** | `fund-realloc.ts reallocateFundSources` | **자금원별 총액(수입−지출) 부족분만** 잉여 자금원(우선순위 [84,83,82], 후원금 85 최후)으로 이동 |
| Pass2 | `item-allocation.ts allocateIncomeToItems` | 자금원 내부 수입을 충당 과목으로 재태깅 |
| Pass3 | `item-balance-zero.ts zeroItemBalances` | (계정×과목) 최종잔액 0 |
| Pass4 | `schedule-expense-dates.ts scheduleExpenseDates` | 지출일 스케줄링(누계≥0) |

- **Pass1의 한도 처리는 "간접적·암묵적"이다.** `fund-realloc.ts:104-110`은 자금원별 **총액 부호**(`netOut−netIn>0` = deficit)만 계산하고, deficit 자금원의 부족분을 잉여 자금원으로 밀어낸다. 잉여 자금원이 받는 양은 `surRemain`(잉여 한도)으로 제한되므로(`:156`, `:170`), **이론상 통장 총잔액 ≥0이면 모든 자금원 최종잔액 ≥0**이 된다(= 배정지출 ≤ 수입). `ledger-allocation.ts:12-14` 헤더가 이를 *가정*으로 명시.
- **그러나 그 불변식을 최종적으로 검증(assert)하거나, 위반을 경고로 표면화하는 게이트가 없다.** `fund-realloc.ts:176`의 shortfall은 이동 계획 단계의 `need>0`(잉여 소진)일 때만 push되며, Pass2~4 이후 최종 자금원별 배정지출이 수입을 넘는지 다시 확인하지 않는다.

### 1.3 근본 원인 (가설 — OQ-1에서 실데이터로 확정)
사용자가 **재배분 후** 산출물에서 초과를 확인했으므로(Q1), 코드상 초과가 살아남는 경로는 다음 중 하나다:
- **(가설 A, 유력) 통장 총잔액 음수** — 전체 지출 > 전체 수입(예: 후원금 수입 일부 미입력). 이때 Pass1은 잉여로 못 메운 부족을 shortfall로 남기고, 초과가 그 자금원(후원금)에 잔존해 산출물에 노출된다. → **가정 붕괴형**. Q3(경고 표면화)로 처리.
- **(가설 B) Pass1 밀어내기 엣지케이스** — 통장은 균형(총수입 ≥ 총지출)인데도, 우선순위/단독충당·환급(음수 지출) 순액 계산(`fund-realloc.ts:100-101`)·확성기 protectIds 상호작용으로 특정 자금원 부족분을 다 못 밀어내 초과 잔존. → **알고리즘 결함형**. Pass1 수정 필요.
- 공통점: 두 경우 모두 **최종 검증 게이트가 없어** 조용히 새어나간다. 본 기능이 그 게이트를 세운다.

### 1.4 부수 발견 — 지출내역관리 '자금원별 충당 현황'은 재배분 SSOT 미적용
`funding-allocation.ts buildFundingAllocation`(지출 입력 페이지 도우미)은 **원본 acc_book**을 그대로 자금원별 집계하고 `overspent: available<0` 플래그만 표시(`:127`). 재배분 SSOT를 거치지 않아, 재배분으로 해소될 초과도 원본 기준으로 과다 표시될 수 있다([[settlement-must-use-realloc-ssot]]와 동일 패턴). Q1 답변은 "재배분 후 산출물"이었으나, 화면·산출물 정합을 위해 본 기능 범위에 포함 검토(OQ-4).

## 2. 목표 / 비목표

### 2.1 목표 (Goals)
- 재배분 후 **모든 자금원(82~85)에서 배정지출 ≤ 그 자금원 수입**을 보증한다(통장 총잔액 ≥0 정상 데이터).
- 이 불변식을 **가정이 아니라 검증되는 계약**으로 승격 — 최종 검증 게이트 + 회귀 테스트.
- 통장 자체가 부족한 경우(총지출>총수입) **0을 강제하지 않고 경고로 표면화**(은폐 금지).
- 모든 재배분 후 산출물에 일관 반영(SSOT 한 곳).
- 원본 acc_book 불변, 자금원별 수입합·지출합·통장 총잔액·지출 과목 **불변**.

### 2.2 비목표 (Non-goals)
- 원본 acc_book 데이터 수정(영구화) — 하지 않음(보고 시점만).
- 지출 과목·금액 변경 — 하지 않음(Pass1은 계정만 이동, 과목·금액 불변).
- 비후보자(후원회 1/2 인코딩) 처리 — 본 건은 후보자(82~85)만.
- 진짜 부족(총지출>총수입)을 0으로 가리기 — 하지 않음(Q3, D-2).
- 자금원 간 대체 재배분 자체를 금지 — 하지 않음(Q2: 대체 허용, 한도만 준수).

## 3. 기능 요구사항 (FR)

- **FR-1 (자금원 수입 한도 불변식 명문화)**: 재배분 후 각 자금원 s(82~85)에 대해 **Σ(배정지출_s) ≤ Σ(수입_s)** 를 1급 불변식으로 정의한다. 한도 판정의 지출·수입 합산 기준(순액/환급 반영 여부)은 OQ-2에서 확정.
- **FR-2 (최종 검증 게이트)**: `buildLedgerRows` 말미(Pass4 후)에 자금원별 `배정지출 − 수입`을 계산해 **초과 자금원·초과액을 검출**한다. 순수 함수(`enforceIncomeCap` 가칭). 초과 0이면 통과, 초과 있으면 FR-3/FR-4 분기.
- **FR-3 (통장 균형 시 한도 내 수렴 보증)**: 통장 총잔액 ≥0(총수입 ≥ 총지출)인데 특정 자금원이 초과(가설 B)면 재배분이 **반드시 한도 내로 수렴**하도록 Pass1을 보강한다(초과분을 잉여 자금원으로 추가 이동). 결과: 모든 자금원 최종잔액 ≥0.
- **FR-4 (진짜 부족 시 경고 표면화·강제 금지)**: 통장 총잔액 음수(총지출>총수입, 가설 A)면 0을 **강제하지 않는다.** 초과 자금원·초과액을 기존 부족 경고 체계(`Shortfall`, `shortfall-surface`)로 **표면화**하고, 데이터(수입) 보완 시 자동으로 0이 되게 한다. [Q3, D-2]
- **FR-5 (자금원 간 대체 허용·후원금 한도 준수)**: 자금원 간 지출 대체(재배분)는 허용하되, **후원금(85)을 포함한 모든 자금원의 수입 한도를 준수**한다. 후원금이 잉여여서 타 자금원 부족을 흡수하는 것 자체는 허용(현행 우선순위 최후), 단 흡수 후에도 후원금 배정지출 ≤ 후원금 수입. [Q2, D-1]
- **FR-6 (불변식 보존)**: ① 지출 과목/금액 불변 ② 자금원별 수입합·지출합 불변 ③ 통장 총잔액 불변 ④ 후보자(82~85)만. → Pass1~4 기존 회귀와 충돌 0.
- **FR-7 (전 산출물 반영)**: SSOT `buildLedgerRows` 수정으로 수입·지출부 뷰어 · HWPX 서식7/22-4 · 회계보고서 22-1 · 결산 · 자료백업(.db) export가 자동 일관 반영. 회귀·parity 테스트로 고정. `funding-allocation.ts`(지출내역관리 현황) 정합은 OQ-4에서 범위 확정.

## 4. 설계 스케치 (Design 단계에서 확정)

```
buildLedgerRows(rows):
  p0..p4 = 현행 (Pass0→L→1→2→3→4)
  cap = enforceIncomeCap(p4)      # 신규 — 자금원별 배정지출 vs 수입 검증
  # cap.rows: 균형 자금원은 한도 내 수렴(필요 시 추가 이동)
  # cap.shortfalls: 진짜 부족(총지출>총수입) 자금원·초과액 경고
  return cap.rows                  # + cap.shortfalls 를 상위로 전파
```

`enforceIncomeCap`(순수 함수, 신규 `lib/accounting/income-cap.ts` 가칭):
1. 자금원별 최종 배정지출·수입 집계(환급 반영 기준은 OQ-2).
2. `over_s = 배정지출_s − 수입_s`. `over_s ≤ 0`이면 통과.
3. 통장 총잔액 ≥0(Σover ≤ 0)인데 `over_s>0`인 자금원이 있으면 → **잉여 자금원으로 초과분 추가 이동**(Pass1 재사용/보강), 한도 내 수렴. [FR-3]
4. 통장 총잔액 <0(Σover>0)이면 → 강제 이동 없이 `over_s>0`을 **shortfall로 표면화**. [FR-4]

**구현 위치 후보 (OQ-3)**: (a) `enforceIncomeCap`를 Pass4 후 최종 게이트로 분리, 또는 (b) Pass1(`reallocateFundSources`) 자체를 "총액 부호"에서 "수입 한도 명시 제약"으로 리팩터. (a)가 변경 최소·검증 명료, (b)가 근본적.

## 6. 엣지 케이스
- **환급(음수 지출, [[negative-refund-rows-in-aggregation]])**: 한도 판정을 **순지출(환급 차감) ≤ 수입**으로 볼지, **양수 지출 총합 ≤ 수입**으로 볼지. 회계 산출물의 시트 잔액은 순액 기준이므로 순지출 기준이 정합 유력(OQ-2). `acc_amt>0` 필터 금지, `acc_amt!==0` 원칙 유지.
- **확성기 앵커(84 강제·protectIds)**: 84로 강제된 확성기가 84 한도에 미치는 영향 — protectIds라 이동 불가이므로 84가 초과하면 다른 84 지출을 밀어내야 함. 84 잉여 여력 재확인.
- **후원금(85)이 흡수 대상일 때**: surOrder 최후라 이미 마지막 흡수. 흡수 후 한도 초과 없는지 검증.
- **다중 deficit·다중 surplus 동시**: 검증 게이트가 자금원 전체를 한 번에 판정(개별 순차 아님).
- **통장 정확히 균형(Σover=0)인데 개별 초과**: FR-3 수렴 대상(가설 B의 핵심 케이스).

## 7. 테스트 계획
- 신규 `income-cap.test.ts`:
  - **통장 균형 + 개별 초과(가설 B)**: 후원금 수입 9,430,000 < 후원금 원지출, 타 자금원 잉여 충분 → 재배분 후 후원금 배정지출 = 9,430,000(한도), 초과 0, 타 자금원도 ≤ 수입.
  - **통장 부족(가설 A)**: 총지출>총수입(수입 누락) → 0 강제 안 함, 후원금 초과 잔존 + shortfall 경고. 수입 보완 픽스처에선 초과 0으로 자동 해소.
  - **환급 포함**: 순지출 기준 한도 판정 정확성(OQ-2 확정안 반영).
  - **불변식**: 지출 과목/금액 불변, 자금원 수입합·지출합·통장 총잔액 불변.
- 기존 `fund-realloc.test.ts`·`item-allocation.test.ts`·`item-balance-zero.test.ts`·`adjusted-ledger-parity.test.ts`(뷰어==export)·`settlement-summary` 회귀 통과.
- **parity 주의([[parity-test-must-exercise-divergence-condition]])**: 초과가 실제로 발생하는 픽스처로 게이트를 트리거할 것(해피패스는 거짓 안심).

## 8. 결정 (확정) / 미해결

### 확정된 결정 (사용자 승인)
- **D-1 (한도 원칙)**: 각 자금원 **수입 한도만 준수** — 자금원 간 대체(재배분)는 허용하되 재배분 후 어떤 자금원도 배정지출 ≤ 그 자금원 수입. [Q2]
- **D-2 (진짜 부족)**: 통장 총잔액 음수(총지출>총수입)면 **0 강제 안 함** — 초과를 경고로 표면화, 데이터 보완 시 자동 해소. [Q3]
- **D-3 (문제 위치)**: 초과는 **재배분 후 최종 산출물**에서 관찰됨 → 검증 게이트를 SSOT 말미에 둔다. [Q1]

### 미해결 (Design에서 확정)
- **OQ-1 (근본 원인 확정)**: 실데이터(오준석후보 .db)로 후원금 초과가 **가설 A(통장 음수·수입 누락)** 인지 **가설 B(Pass1 밀어내기 엣지케이스)** 인지 진단. A면 FR-4(경고) 중심, B면 FR-3(Pass1 보강) 필수. → **Design 착수 전 선행 진단 권장.**
- **OQ-2 (한도 판정 기준)**: 순지출(환급 반영) ≤ 수입 vs 양수 지출 총합 ≤ 수입.
- **OQ-3 (구현 위치)**: 최종 게이트(`enforceIncomeCap`) 분리 vs Pass1 리팩터.
- **OQ-4 (`funding-allocation.ts` 정합 범위)**: 지출내역관리 현황을 본 기능에서 재배분 SSOT로 통일할지, 별도 후속으로 분리할지.
- **OQ-5 (경고 UI)**: 기존 `shortfall-surface`/부족 경고에 "자금원 수입 초과" 케이스를 어떻게 노출할지(문구·위치).

## 9. 리스크
- **근본 원인 미확정**: OQ-1을 실데이터로 진단하지 않고 설계하면 헛발질 위험(가설 A vs B가 해법을 가름). Design 첫 단계로 진단 고정.
- **SSOT 광범위 영향**: `buildLedgerRows` 말미 게이트가 6개 산출물에 전파 → parity/회귀 테스트 필수([[export-db-accbook-split-bak-raw]] 비대칭 유지).
- **회계 정당성**: "자금원 간 대체는 허용하되 한도 준수"의 법적 근거를 Design에서 명문화(후원금 용도 제한 vs 총량 대체 가능 여부는 회계 원칙 확인).
- **환급 부호 처리**: 한도 판정에서 환급 음수 누락 시 과대/과소 계상([[negative-refund-rows-in-aggregation]]).
